PaymentProvider interface with two implementations: MOCK (a fake hosted payment page with Success and Failure buttons for local testing, default in development) and RAZORPAY (test mode first; orders created on the server, Razorpay Checkout on the client, allow its script in the content security policy, webhook with signature verification, idempotent handling, refunds). CP-7: TUTOR RATES AND EARNINGS, 1:1 AND GROUP CLASS PRICING, MY REQUEST
=====================================================
1. Tutor rate card (set by the Org Admin in Create Tutor and Tutor Details; tutors see theirs read-only): oneToOneRatePerSession (with a standard duration, default 60 minutes) and groupClassRatePerClass
2. Class kinds in Experts Session: GROUP (included in the subscription by default; optionally "paid extra" with a per-seat fee), ONE_TO_ONE (a private room for the tutor and one student, paid per session), WEBINAR (a course-wide session, free or paid). Student price for a 1:1 session = the tutor's oneToOneRate plus the organization margin percentage, calculated on the server and shown before payment
3. Earnings ledger: when a class is completed (the tutor ended it and at least one student attended; for 1:1 both attended) create a TutorEarning (tutorId, sessionId, kind, amount, status PENDING then PAYABLE then PAID). Group class earning = the group rate per class; 1:1 earning = the 1:1 rate. Org Admin "Tutor Payables": per tutor totals, per class lines, a "Record payout" action (amount, method, reference, date) that marks earnings as PAID, with an AuditLog entry and a CSV export. Tutor "My Earnings": rate card, earnings per class, monthly totals, payout history, statement download. Payout is recorded manually; automatic splits (for example Razorpay Route or Stripe Connect) are out of scope and must be mentioned in the README
   - Optional payout details of tutors (UPI ID or bank account): ask me before storing anything; if stored, encrypt at rest (AES-256-GCM with a key from the environment), mask it in the UI, show it only to that tutor and the Org Admin, and log every access
4. My Request (student module)
   - Student creates a request: type (1:1 session, group class or topic request, doubt clarification, material request), course, preferred tutor (tutors assigned to that course with their bio and rates), up to three preferred date and time slots, duration, and a message. Limits: a maximum number of open requests per student (setting, default 5) and rate limiting
   - Status flow: PENDING, then ACCEPTED (the tutor picks a slot), DECLINED (with a reason), RESCHEDULE_PROPOSED (the student accepts or rejects), CANCELLED, EXPIRED (no reply within a configurable time), COMPLETED. A short message thread on each request
   - When a 1:1 request is accepted: the student sees the price and a Pay button (when payments are enabled); after payment a ONE_TO_ONE session is created automatically with a private room, in the student's and tutor's Experts Session lists, with notifications and reminders. When payments are disabled the session is confirmed directly
   - Group class or topic requests: the tutor can answer with a scheduled GROUP or WEBINAR session; interested students are notified
   - Tutor portal: a "Requests" inbox with filters, accept, decline, propose another time, and a link to the student's course progress. Org Admin sees all requests and can reassign a request to another tutor. Notifications on every step
5. Seed: tutors with rate cards, earnings from past classes, a few payouts, requests in different statuses for demo students, one paid 1:1 session
6. Tests: the request state machine and permissions, price calculation for 1:1 sessions, private room access (only the two participants), earnings creation only for completed classes, payout recording and totals, notifications on each step, students cannot see other students' requests or payments, organization isolation
